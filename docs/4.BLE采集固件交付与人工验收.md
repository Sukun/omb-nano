### 3.2 识别实际 CH340 串口

macOS 上 CH340 通常呈现为 `/dev/cu.wchusbserial*` 或 `/dev/tty.wchusbserial*`。用以下任一方式确认，**不要凭记忆填写端口**：

```sh
ls /dev/tty.* | grep -i usb
ls /dev/cu.*
python3 -m serial.tools.list_ports -v     # 需要 pyserial；可用 conda 环境 python
```

插拔 USB 前后各执行一次 `ls /dev/cu.*`，新增的那一项即本板端口。记录实际路径（例如 `/dev/cu.wchusbserialXXXX`），下文用 `<实际串口路径>` 代替。

### 3.3 关闭占用串口的程序

```sh
lsof /dev/cu.wchusbserial*      # 列出占用者；逐个关闭
```

- 退出 `screen`（会话内按 `Ctrl-A` 再按 `K`，确认 `y`）。
- 关闭 `imu_listen.py`、`hardware_test.py --monitor`、`run_experiment.sh`、串口监视器、Bleak 接收端等一切占用程序。
- 重新执行 `lsof` 确认无输出后再烧录。

### 3.4 核验固件身份

```sh
cd ~/Documents/omb-nano
shasum -a 256 firmware/omb_nano_ble_capture.bin
```

必须得到 `e60189e82a3fd78b84e94e98bd8f5e53e3016facfbe139391570d8e9342ad415`，且大小为 230968 字节。不一致则停止，不要烧录。

### 3.5 SVL 烧录命令（候选命令，逐字来自 PLAN_04 §B）

```sh
python3 firmware/svl_flash_v2.py <实际串口路径> -f firmware/omb_nano_ble_capture.bin -b 115200 -v --frame-size 16 --frame-delay 0.15
```

- 依赖 pyserial（`conda activate pcb` 或等价环境）。
- 若提示 “Failed to enter bootload phase”，先检查 3.3V 供电与 USB 连接；若提示 “Error receiving packet”，保持 `--frame-size 16 --frame-delay 0.15` 并检查供电稳定性。
- 烧录耗时较长（历史记录约 7 分钟量级），期间不要断电或插拔。

### 3.6 启动与 BLE 广播检查

烧录完成后板子复位进入 BLE 采集模式。用 PLAN_03 接收端的扫描模式确认广播：

```sh
python3 -m venv .venv-ble-receiver          # 首次
.venv-ble-receiver/bin/pip install -r firmware/requirements-ble-receiver.txt
.venv-ble-receiver/bin/python firmware/ble_capture_receive.py
```

- 未加 `--address` 时脚本扫描 10 s，查找广播名 `OMB-Nano`；找不到会报“未发现广播名为 OMB-Nano 的设备”。
- 发现后脚本自动订阅 Data 特征（`…0003`）并向 Control（`…0002`）写 START，进入一次 600 点采集；每次运行在 `firmware/ble_captures/`（或 `--out`）下新建含 run_id 的独占目录，不覆盖历史结果。
- 结果以 `结果: COMPLETE（正式 CSV 已确认）` 或 `结果: INCOMPLETE` 输出，并列出会话目录、诊断日志、正式 CSV 或 `.partial` 路径。
- 注意：该工具没有独立的“仅扫描”模式，发现设备后会立即连接、订阅并写入 START，因此一次运行就是一次完整采集，可作为第 6 节阶段 1/2 的证据。若只想确认广播，应在连接后尽快中断（`Ctrl-C`），此时板端已开始采集，电脑端会保留 `.partial` 与诊断日志，该次结果不计入正式验收。
